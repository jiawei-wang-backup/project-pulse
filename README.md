# Project Pulse

团队开发活动看板。每位成员电脑上的 Codex 识别项目、会话、GitHub PR、模型和真实 Token 用量，整理脱敏摘要、项目目标与里程碑，每 30 分钟增量同步到服务端。

客户端先自行查找和核验，仍缺信息或证据冲突时才询问用户。固定脚本负责解析、差分、续传和提交，服务端校验、去重、存储与展示。

项目详情有独立的「功能模块」区，用名称和简短介绍展示项目包含的功能，与里程碑分开。客户端可随项目报告补充模块；部署需应用 `012_project_modules.sql`。

## 下载上报包

**[下载中文局域网接入包 v3.6.0-r2（ZIP）](https://github.com/jiawei-wang-dev/project-pulse/releases/download/report-client-v3.6.0-20261117/project-pulse-report-3.6.0-lan-r2.zip)**

ZIP 可直接从 GitHub 下载。解压后，授权和上报需要连接团队局域网。

解压后，用 Codex 打开目录并发下面的提示词。选好项目和频道、完成网页授权后，Codex 会继续试报、发布已提交的脱敏进展并设置自动同步。首次使用时如需信任 HTTPS 证书，按 ZIP 内说明操作。

```text
请直接完成接入。用当前解压目录的 README.md、PROMPT.txt、project-selection.md 和包内工具，不要让我手填服务端地址、编辑配置或另发提示词。

运行 pulse-onboard.py links 核对两个服务端并记下地址。只读识别本机项目，在同一条消息一次列出编号，请我选择需要上报的项目和各自要发布进展的 Ember 频道名称。允许只上报到看板。不要默认全选或自行选频道。

根据我的选择运行 ember-connect.py connect。需要发布进展时加 --write；目标频道需要私有权限时才加 --private。把命令输出的授权链接发给我，等待我用本人账号授权，不要代我点允许或索取凭证。授权完成后运行 ember-connect.py rooms，核实发布目标是我指定的频道，再保存私有 .pulse-project-selection.json，给对应已选项目记录 ember_room_id。频道匹配不唯一时才询问，不猜频道。

随后立即按 PROMPT.txt 完成试报。运行 pulse-onboard.py prepare，使用真实的本轮会话 UUID 排除接入会话。根据返回的脱敏证据在 work_dir 中准备有依据的 summaries.json、pulls.json 和 statuses.json；有新进展就写项目目标和里程碑。随后运行 pulse-onboard.py submit --work-dir <本轮返回目录>。脚本会核对 Project Pulse 回执，并把已提交的脱敏进展发布到已绑定的 Ember 频道。核对 report、ember_posts 和 ember_error。没有新进展时不发空消息。不要把网页授权成功当成发布成功。

试报后用可用的定时任务工具创建或更新原有的「Project Pulse 每30分钟上报」，在本目录用同一 prepare、整理、submit 流程。以后沿用已确认的项目和频道，不重复询问，也不自行加入其他项目或改频道。任务工具不可用时保留已完成的试报并说明限制。

结束时主动给出可点击的 Ember 工作区、已同步频道及 Project Pulse 看板链接（取自脚本结果），并分别说明看板回执、Ember 发布、定时任务是否成功。失败时也返回服务端地址和实际卡住的步骤。
```

## 仅配置项目上报

1. 解压到长期保留的目录，例如 `Documents/project-pulse-report`。不要在 ZIP 预览或临时目录里运行。
2. 用这台电脑上的 Codex 打开解压后的 `project-pulse-report` 文件夹。
3. 复制下面整段提示词发送给 Codex。它会先列出本机项目供你选择，等你确认后仅上报所选项目，再创建或更新每 30 分钟同步任务。

```text
PROJECT_PULSE_AUTOMATION。读取当前目录的 PROMPT.txt 和 README.md，先按project-selection.md只读列出本机项目让我选择，等我确认后再对所选项目执行完整上报与定时同步流程。

第一步只做只读盘点：列出项目编号、仓库或本地工作区、已识别主会话数量及待确认项，让我多选。选择前不得执行Prepare／Submit、上传或设置任务，不默认全选。确认后保存私有选择文件；每轮Prepare和Submit必须限制OnlySource为所选项目，后续30分钟任务沿用此范围，新项目先询问再加入。

我授权你识别本机 Codex 主会话及相关项目、成员、GitHub仓库和PR、模型与真实Token用量，并生成脱敏摘要、项目目标和里程碑。先主动查找并复用已有信息，仍缺信息或证据冲突时，再集中询问我。排除当前上报会话，不编造数据。

使用包内对应系统的固定脚本，向 http://192.168.20.47:4185 增量上报。一个所选业务项目可关联多个仓库：查证每个真实仓库及数字ID，按README写repositories.json；PR按实际仓库与编号提交，不伪造单仓库归属。先核对服务端multi_repository_projects能力。PR也要按README查证并结构化提交，分别核对日志、Token和PR回执。

每轮先读私有项目选择，并用 Inventory 查询所选项目和本机已授权会话在面板上的已有信息与缺项，再开始准备上报。只补有证据的缺项和经确认的新信息。已有内容、项目归属或待发批次与本机证据冲突时，先列出差异询问用户，等待确认再处理冲突项。定时运行把问题留在结果里，继续同步范围内其余无冲突数据。提交后重新查询核对。

每轮检查所选项目的功能模块。服务端支持 project_modules 时，根据项目 README、代码和已确认成果整理 1–12 项，每项写模块名称和一句职责介绍。首次缺失或有变化时提交完整 modules 清单，并核对项目报告是否显示。无新增日志时按项目报告补报流程提交，沿用原游标和计量上下文。证据不足或服务端尚未启用时，在结果里说明。

项目状态由会话证据判断，在研包含尚未完成的阻塞项目；不按时间超时，与Agent执行状态分开。状态变化或首次补齐时按README提交statuses.json并核对status_receipt，不把一轮任务结束当作整个项目完成。

需要修正团队记录时，先核对服务端team_metadata_edit能力，再按team-edits.md查询目标成员、设备、会话与最新version，带原因提交并核验。允许修正全员的摘要、项目归属、目标、里程碑和状态；证据不足先询问，不改原始Token或游标。正常上报不为使用此接口而改写其他成员数据。

试报成功后，必须使用定时任务工具，创建或更新并启用「Project Pulse 每30分钟上报」，每30分钟在当前永久解压目录执行完整识别与增量同步。已有同用途任务就更新，避免重复；设置后重新查询确认启用状态、间隔和目录。无需再次询问是否设置。

最后报告实际识别及提交结果、Token与PR核验结果、积压和缺失信息，以及任务标识、启用状态和计划规则。无法上报或无法设置任务时明确说明失败步骤和原因，不得宣称全部完成。
```

当前服务端是 `http://192.168.20.47:4185`，客户端必须能访问它。客户端自己的 IP 不是服务端地址，不要替换。私有仓库与 PR 使用本机已授权的 GitHub 只读工具；权限不足时由 Codex 说明缺少什么，不把凭证发进聊天。

## 同步哪些数据

| 数据 | 客户端 Codex 的工作 |
| --- | --- |
| 成员与设备 | 核对团队目录和已确认身份；换 Codex 账号不自动变更团队成员 |
| 项目与目录 | 核对 Git remote，结合会话、README 和近期提交识别同名目录及迁移关系 |
| 会话与摘要 | 使用原生会话 ID，排除当前上报会话，复用历史摘要，只总结新增成果 |
| 模型与 Token | 从日志解析模型、输入、缓存输入、输出 Token，按游标计算差分，不估算或重复累计 |
| GitHub PR | 查证仓库数字 ID、PR 编号、状态和时间，结构化提交并核对独立回执 |
| 目标与里程碑 | 依据证据总结目标、已完成及未完成交付项，不编造进度 |
| 项目状态 | 根据会话判断在研、阻塞、完成或明确暂停，独立上报状态与依据，不按时间超时 |
| 30 分钟任务 | 试报成功后必须设置，再查询确认启用状态、间隔和工作目录 |

日志提交核对 `committed`、`usage_verified`，PR 提交核对 `pr_receipt`。无新增、缺少记录、权限不足、解析失败和仍有积压必须分别说明；面板没有 PR 不等于 GitHub 没有 PR。只有查到任务存在才能说“已设置”，实际自动触发成功后才能说“自动运行已验证”。

## 支持的系统

| 系统 | 入口 | 系统依赖 |
| --- | --- | --- |
| macOS | `pulse-report.pl` | Perl、curl |
| Windows | `pulse-report.ps1` | Windows PowerShell、curl.exe |
| Linux | `pulse-report-linux.sh` | Perl（含 JSON::PP、Digest::SHA）、curl |

执行工具需要能读取本地文件、运行命令并连接服务端。定时功能由实际执行工具提供；没有该能力时必须明确报告“未设置”，不能把脚本能运行当作定时任务已启用。

## 更新已有客户端

下载新 ZIP，覆盖原永久解压目录，保留 `.pulse-state-*.json`、`.pulse-project-paths.json`、`.pulse-project-selection.json`、`.pulse-pending/`，再发送上面的提示词。更新原任务的正文并重新核验，不重复创建。待发请求先恢复，不清空游标或重新导入历史 Token。

当前包3.6.0使用协议3。真正服务端需先执行009_project_lifecycle迁移并重启，提供 `usage_receipt`、`project_mapping_backfill`、`client_pr_ingest`、`client_project_status` 能力。Agent识别窗口现为2小时，并补足缺少开始事件的活动识别；已完成、取消或失败的任务不因此复活。更新ZIP不会自动更新另一台电脑的服务端或已存在的定时任务。

## 服务端与开发

以下只在真正服务端或开发环境执行，成员上报电脑无需执行。

- Node.js 24+，运行 `npm ci` 和 `npm start`；未配置数据库时默认在 `http://127.0.0.1:4174` 展示演示数据。
- 真实数据使用 PostgreSQL；迁移、局域网部署、备份及独立令牌模式见 [服务端部署说明](docs/deployment.md)。
- 客户端可通过 [团队数据修正接口](docs/team-edits.md) 修改全员的摘要、项目归属、目标、里程碑和状态；真正服务端需应用010迁移并启用 `PULSE_TEAM_EDITS=1`。
- `npm test` 运行测试；在可丢弃的已迁移数据库设置 `DATABASE_URL` 后运行 `npm run test:integration`。便携采集器 CI 覆盖 macOS、Windows 和 Ubuntu。
- 构建上报包：`sh ops/report/build-package.sh /绝对路径/project-pulse-report-3.6.0.zip`。包内不包含本机状态、路径映射、日志或凭证。

## 从 Ember 查询看板

在已绑定的研发进度看板频道里，输入 `@` 并选择「研发看板试点」，可以问「这个项目还差什么？」或「今天早上九点前有几台电脑上传成功？」。

项目进度来自最新的项目报告，回答会注明报告日期。上传台数来自本机 PostgreSQL 的成功回执，按设备去重。镜像服务的 `GET /api/v1/local-upload-counts` 仅接受本机请求，返回今天和今天截至上午九点的全团队台数，时区取自服务端。九点前第二项为空；从旧服务器导入的看板摘要不包含逐台上传回执。
