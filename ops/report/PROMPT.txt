允许脚本仅为这些授权会话只读查询其工作目录的 Git remote 来识别项目，使用 ResolveGit 选项。先查询团队目录，已知且由用户确认的 GitHub 账号使用 GitHubLogin 选项；不能按仓库拥有者或提交作者认定成员，无法确认时询问账号或姓名，无人值守时沿用已保存身份。工作目录使用本包 .pulse-pending 下的随机新子目录，失败保留以便下轮自动重试，不把状态文件放进临时目录，不清空已确认游标。

Codex更新、换号或迁移后不能假定日志仍在旧目录。每轮使用脚本的有界目录发现：当前CODEX_HOME、当前用户默认目录、已确认的历史根目录以及Codex候选账号目录。不同目录里的同一原生会话ID沿用同一游标，不能按路径或当前Codex登录账号重新生成设备／会话标识；Codex订阅账号切换也不自动改变团队成员。核对diagnostics.session_roots_found和discovery_incomplete；根目录为0、没有可读日志、目录扫描未完成或source_header_changed_requires_confirmation时，先上报已确认数据，再明确反问“Codex是否更新／换号／迁移？请提供当前CODEX_HOME或会话sessions目录”，不得报告零消耗或全部同步完成。用户确认的新根目录用SessionRoot／--session-root传入Prepare并持久化；不搜索其他用户目录或读取登录凭证。

会话元数据中的项目cwd也可能是旧路径。客户端Codex必须先按README的“项目工作目录迁移”自行识别同名／迁移目录：结合已授权会话的项目摘要、候选目录README、Git remote与近期提交，总结判断是否属于同一项目。证据一致且候选唯一时，直接把旧路径→新仓库路径写入本包私有 .pulse-project-paths.json，并保留一条简短识别依据，无需再次请用户确认；用ResolveGit核对真实remote，再重新Prepare（使用新的待续传目录）以应用映射。不能看到旧路径失效就立即要求用户手填；先完成有界候选查找和内容判断。只有候选不唯一、证据不足或存在冲突时，才在提交已确认数据后集中反问。即使无新增日志，也要提交脚本生成的mappings归属补报（usage为0、游标不变）；服务端缺少project_mapping_backfill能力时明确要求真正服务端升级，不以重置游标重导Token代替修复。

必须通过固定脚本增量上传 Token 消耗：模型、输入 Token（input_tokens）、缓存输入 Token（cached_input_tokens）、输出 Token（output_tokens），并保留事件时间与会话关联。用量必须取自授权日志，通过服务端游标计算差分，禁止估算、编造或重复累计。即使本轮没有新的摘要或里程碑，也必须提交新增 Token 用量，不能只上传项目总结。

项目状态由客户端Codex结合授权会话、已有目标／里程碑和上一版状态判断，按README写statuses.json并核对status_receipt。on_track表示已开始、未完成且未暂停；blocked表示仍在研但有明确未解决阻塞，二者都计入面板“在研项目”。completed必须有整个项目目标已达成的证据，单次任务结束、PR合并或Agent空闲不能证明项目完成；paused必须有明确暂停决定。没有证据时沿用上次状态，首次无法判断才unknown并说明缺什么。不因下班、开会、会话关闭、没有新Token或长时间没活动而暂停、阻塞或完成项目；项目状态没有时间超时，与running／idle等Agent执行状态分开。状态有变化或首次需补齐时即使无新增日志也提交，不能只在摘要里描述状态。

Agent执行采用较宽松的活动识别：缺少task_started时，新的普通用户消息、模型输出／推理、工具调用或未知状态下的新增Token也能表明正在工作；明确task_complete或turn_aborted后保持终止状态，尾部计量快照不得复活已结束任务。看板对明确running保留2小时活动窗口；旧客户端unknown状态只有近30分钟实际用量证据才暂计运行中。同步动作本身不算业务Agent活动，也不能用此窗口改变项目生命周期。

PR由客户端Codex主动识别和上报：从已授权且可用的GitHub只读工具查证仓库数字ID及PR（含open／closed／merged／draft），按README结构写入本轮待续传目录的pulls.json，使用同一个Submit提交到服务端并核对pr_receipt。无新增会话或Token时仍要检查已识别项目的PR更新；不能等待服务端定时抓取代替客户端识别。面板无记录不等于GitHub没有PR；无权限、工具不可用、查证失败、超出本轮查询范围时说明原因与覆盖范围，先上报其他可确认数据，再反问需要的仓库／PR信息，不能捏造数字ID或用量，不能把PR链接写进会话摘要冒充结构化PR上传。

上报结束后必须逐项披露未识别／未核验的数据：成员身份、项目仓库映射、PR、模型和三类Token、会话摘要、项目目标与里程碑。每项写明项目、缺失字段、已检查证据和具体原因。先提交能够确认的数据、完成可以执行的任务步骤，再在最终回复中向用户集中反问缺失的最少信息，例如“项目X未识别到PR，请提供GitHub仓库地址或PR链接／编号；项目Y无法确认成员，请提供GitHub账号或姓名”。已有答案不得重复询问；本轮无新增、确实不适用的项不列为未识别。不能仅列出缺失就结束，也不能用猜测补齐或宣称全部完整。无人值守运行也必须把待确认问题留在任务结果中，不阻塞已确认数据的上报。

先确认服务端可访问，再执行 Prepare 和 Submit。核对 Prepare 的 usage 汇总及 diagnostics。只有 Submit 获得 committed 且 usage_verified 为 true（服务端回执的事件数、输入／缓存输入／输出 Token 与请求逐项一致），或已成功查询有效来源游标且检查范围内没有新批次、没有解析错误，才算试报通过。还有积压时明确本轮并未同步全量；无日志或全部被排除不算成功试报。Dashboard 可辅助检查显示，但不能用7天展示窗口否定较旧积压的成功提交。没有用量时必须区分无新增、缺少用量记录、解析失败或积压未读到。unmeasured_snapshots 大于0时说明存在无法确定的用量，不得编造或报告计量完整。

试报成功后必须继续执行：查找 Codex 桌面端的定时任务工具（automation_update），查询当前电脑已有任务，直接创建或更新并启用「Project Pulse 每30分钟上报」。每 30 分钟在当前解压后的永久目录运行；已有同用途任务就更新并启用，不重复创建。任务正文使用 README.md 里给出的固定文本。不能在上传成功后结束、只给用户创建步骤，或把 README 中的定时要求当成可选建议。backlog: true、本轮无新增用量或沿用已有摘要均不能成为跳过定时任务的理由。

设置后必须重新查询任务，核对它已启用、间隔为 30 分钟、工作目录正确。最后分别回报：服务端地址、试报回执、提交批数、输入／缓存输入／输出 Token 增量及服务端核验结果、是否有积压、任务名称、任务是否已启用、下次运行时间。如果当前工具没有定时任务能力，不得声称设置成功，要明确说「未设置」及原因。

最终回报还必须包括项目／会话识别结果、PR已查范围、PR实际提交条数和pr_receipt，以及仍缺少的信息与集中反问。每30分钟任务同样完整执行上述识别、PR查询、Token增量、摘要及里程碑更新和回执核验；已知无变化数据可以复用，不从头重复总结。

还要报告本轮项目状态判断与依据，以及status_receipt；保留无变化的既有判断，不按时间刷新或制造状态变化。

完成条件：试报成功，并且重新查询确认定时任务存在且已启用。回报任务工具返回的任务标识和实际计划规则；若工具未提供下次运行时间，明确写“工具未提供”，不要编造。若试报失败或任务工具缺失／报错，明确报告“整体未完成”、失败步骤和具体错误，不得将一次试报成功描述为全部配置完成。定时运行本身仅执行一轮上报，不重复创建任务。

区分“已设置”与“自动运行已验证”：只有至少一次由调度器触发的运行完成并有提交回执或有效无新增诊断后，才可报告自动运行已验证。首次只创建了任务时明确报告“已设置，首次自动运行待验证”。

团队数据修正：服务端目录声明team_metadata_edit时，按包内team-edits.md使用团队查询与修正接口，可修改所有成员的摘要、项目归属、目标、里程碑和状态。必须有用户要求或核实依据；先读取目标设备与会话的最新version，再带原因提交，核对committed回执并重新查询。证据不足先集中询问，409版本冲突则重新核对，不强制覆盖；重试保留原请求ID和正文。后续上报参考服务端最新信息，不用旧本地缓存恢复已纠正的数据。不能修改原始Token、同步游标、设备凭证或成员身份。没有此能力时说明服务端需应用010迁移并启用PULSE_TEAM_EDITS=1，不得宣称已完成修正。无实际修正需求时照常增量上报，不为使用新接口而扫描或改写全员记录。
